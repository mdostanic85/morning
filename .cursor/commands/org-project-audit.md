## Required finding: the Lucas collision

This section is **mandatory**.  Do not skip or abbreviate it.

The roster contains two people named Lucas:

- **Lucas Saeed** — Design Team Lead, depth 2, reports to David Brubacher
  (CPO/COO).  He is the intended high-authority stakeholder.
- **Lucas Thomas** — Software Engineer, depth 4.  He has no management
  authority.

**How `hasHighAuthorityStakeholderInstruction` matches them:**

The function (site 3 above) tests `\bLucas\b` against the full source haystack
(author + title + body).  A transcript quoting Lucas Thomas passes this test
identically to one quoting Lucas Saeed.  The `+160` boost (site 4) is then
applied, and the `"Explicit instruction from Matt or Lucas"` reason is stored
in the decision trail.

**Blast radius:**

1. A task mentioned by Lucas Thomas in a Jira comment or transcript receives a
   +160 score boost it should not have, potentially displacing higher-priority
   work from the focus view.
2. The decision trail shown to the user (`DecisionTrail.tsx`) attributes the
   boost to "Matt or Lucas" — the user cannot tell which Lucas triggered it.
3. The LLM prompts (sites 8–11) are told to treat any "Lucas" as high-authority.
   The LLM has no way to resolve the collision either.
4. `decisionEngine.ts` (site 6) uses a substring match (`.toLowerCase().includes`)
   which is even wider than the word-boundary regex — it would fire on any source
   author field containing the substring "lucas" (e.g. `lucas.thomas@spaceinch.com`).

**Correct fix direction (to be proposed, not implemented here):**

Replace bare first-name matching with full-name + role check against the roster.
The test in site 14 must be updated to match the new reason string.

## Identity-resolution regression analysis

Read `src/lib/tasks/personIdentity.ts` in full before writing this section.

`resolvePersonIdFromAliases` has two resolution paths:

1. **Exact alias match** (line 42–44): unambiguous if exactly one person holds
   this alias.
2. **Unambiguous first-name fallback** (line 47–53): returns a match only when
   exactly one existing person shares that first name.

**Current state (sparse `people` table, pre-roster import):**

With few people in the table, first-name fallback often resolves correctly
because no collision exists yet.

**Post-roster state (92 rows imported):**

The 10 colliding first names from `docs/org/hierarchy-decoding-rules.md` will
cause the first-name fallback to return `null` for all 27 affected people:

| First name | People sharing it | Effect |
|---|---|---|
| ivan | 7 | All "Ivan" references become unresolvable |
| luka | 4 | All "Luka" references become unresolvable |
| lucas | 2 | **Lucas Saeed and Lucas Thomas both unresolvable by first name** |
| david | 2 | unresolvable |
| mateo, karlo, neven, goran, alex, ante | 2 each | unresolvable |

**Effect on `ownerFilter.ts`:**

`ownerFilter.ts:361` (`ownerFilterLabel`) and the filter function rely on
`resolvePersonIdFromAliases` to match the `owner` query parameter to a person
record.  Post-import, filtering tasks by any of the 10 colliding first names

the intended filter stops working.

## Project classification

Classify every person in the roster by project using only deterministic signal
from the local database.  No LLM.  No invented membership.

### Signal sources (in priority order)

1. **`source_items.author`** — Jira reporter display name stored by
   `src/lib/connectors/jira.ts` (L123, L219).  Join to project via
   `projects.jiraKeys` matching the Jira key prefix in `source_items.url`.
2. **Assignee parsed from Jira body text** — `Assignee: <name>` lines
   (jira.ts L130–131, L227–228).  Same join.
3. **`source_items.metadata.involvement = 'assignee'`** — 24 rows with this
   field.  Prefer over body parse when available.
4. **Calendar attendees** — `metadata.participants` array on calendar source
   rows.  Join to project via calendar organizer's email domain or meeting title
   keywords matching project names.
5. **Gmail senders/recipients** — `metadata.from`, `metadata.to`.  Match to
   roster names using `normalizePersonName` (diacritic-fold + lowercase).  Email
   `lucas.saeed@spaceinch.com` → Lucas Saeed.
6. **GitHub logins** — `source_items.author` on github rows, joined to project
   via `projects.githubRepos`.

### Name reconciliation required

Before joining, normalize these non-standard forms:

- Email-wrapped: `Lucas Saeed <lucas.saeed@spaceinch.com>` → `Lucas Saeed`
- Username: `connor.mclaren` → `Connor McLaren` (dot-separated camelCase split)
- External email: `connor@woodlandrussell.com` → treat as `Connor McLaren`
  (external address documented in plan)
- Non-roster people `Brian Dailey` and `Erin Rose` are **external** — do not
  invent a roster entry for them.  Classify them as `external` and note all
  projects they appear in.

### Output format (one row per person × project)


## Implementation proposal

Write this section last, clearly **separated from audit findings**, under the
heading `## Proposed implementation (not yet implemented)`.

The proposal must cover:

### 1. Schema

New or amended tables:

```sql
-- org_roster: one row per person from si-org-chart.json
CREATE TABLE org_roster (
  id           SERIAL PRIMARY KEY,
  figma_node_id TEXT UNIQUE NOT NULL,
  name         TEXT NOT NULL,
  normalized_name TEXT NOT NULL,  -- normalizePersonName(name)
  title        TEXT NOT NULL DEFAULT '',
  location     TEXT NOT NULL DEFAULT '',
  manager_id   INTEGER REFERENCES org_roster(id),
  depth        INTEGER NOT NULL DEFAULT 0,
  extracted_at TIMESTAMPTZ NOT NULL,
  source_version INTEGER NOT NULL DEFAULT 1
);

-- org_roster_alias: additional name forms (email, username, etc.)
CREATE TABLE org_roster_alias (
  id        SERIAL PRIMARY KEY,
  roster_id INTEGER NOT NULL REFERENCES org_roster(id),
  alias     TEXT NOT NULL,
  alias_type TEXT NOT NULL  -- 'email' | 'username' | 'display_name'
);

-- project_membership: evidence-backed project affiliation
CREATE TABLE project_membership (
  id          SERIAL PRIMARY KEY,
  roster_id   INTEGER REFERENCES org_roster(id),    -- null for externals
  person_name TEXT NOT NULL,                          -- raw name as found
  project_id  INTEGER NOT NULL REFERENCES projects(id),
  role        TEXT NOT NULL DEFAULT 'contributor',   -- 'reporter' | 'assignee' | 'attendee' | 'author'
  evidence_source_id INTEGER REFERENCES source_items(id),
  evidence_date TIMESTAMPTZ,
  evidence_quote TEXT,
  is_external BOOLEAN NOT NULL DEFAULT FALSE
);
```

### 2. Service layer

Replace name-string stakeholder checks with role and reporting-line lookups:

- `isHighAuthorityStakeholder(authorName, rosterRows)` — returns true only when
  the normalized full name matches a roster row with depth ≤ 2 (i.e. reports
  directly to CPO/COO or CEO).
- `escalationPath(name, rosterRows)` — returns the chain of `managerName`
  values one at a time.
- `resolvePersonFromRoster(name, rosterRows, aliases)` — replaces the current
  first-name fallback with full-name exact match + alias match.  Returns `null`
  on ambiguity; does not fall back to first-name when two people share it.

### 3. Migration path for stale `projects.people` arrays

4 projects currently have `people` arrays populated; `Brian Dailey` is in one
and is not in the roster.  Steps:

1. Cross-reference each name against the new `org_roster` table.
2. Insert matched names as `project_membership` rows with `role='legacy_people_array'`
   and `is_external=false` (or `is_external=true` for Brian Dailey / Erin Rose).
3. Clear the `projects.people` column once all rows are migrated.

### 4. Test list

At minimum:

- **Regression: Lucas Thomas must not receive stakeholder authority** — create
  a transcript authored by "Lucas Thomas", run `sourceAuthorityScoreBoost`, assert
  the `+160` boost is absent.
- **Lucas Saeed receives authority** — same test with "Lucas Saeed", assert
  `+160` present.
- **First-name collision produces null** — after importing both Lucas rows into
  `org_roster_alias`, assert `resolvePersonFromRoster("Lucas", …)` returns null.
- **Escalation path is one level at a time** — assert `escalationPath("Miloš Dostanić")`
  returns `["Lucas Saeed", "David Brubacher", "Joshua Segall"]`.
- **`priorityExplanation.test.mts`** — update the asserted string at line 10
